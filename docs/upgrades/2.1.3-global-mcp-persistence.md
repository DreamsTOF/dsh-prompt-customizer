# 2.1.3 — 全局 MCP 持久化修复

版本 2.1.3，宿主契约不变（`engines.dsh: ^0.2.2-rc.1`）。本次修复一个“全局 MCP 添加后重启丢失”的持久化缺陷，根因由实读宿主启动流程与真实 DSH web profile 复现定位。

## 缺陷：全局 MCP 添加后重启丢失

面板“添加 MCP Server（全局）”走 `POST /api/triad/mcp-config` 的 `action: add`。旧实现调用 root Include 树的 `tree.create()`：

- DSH 的 `runProfile()`（`apps/cli/src/profile-boot.ts`）与 `prepareProfile()` 在每次启动时都会把 profile 根 `cordis.yml` 重写为 `PROFILE_ROOT_CONFIG`（空数组）：注释明确是防止 Loader tree write-back 把组合行“烤”进根文件、导致下次启动重复插入。
- root Include 树没有对应 patch 的运行时新增行，最终由 `cordis-plugin-include` 的 journal 写进 `cordis.yml`；于是添加当下 status 可见，下一次启动被启动器清空。
- 真实复现（DSH 0.2.2-rc.1，临时 web profile）：添加 `zz-repro` 后 `cordis.yml` 出现该行、`cordis.patch.yml` 不变；重启后 `cordis.yml` 回到 `[]`，`GET /api/triad/mcp-status` 不再有 `zz-repro`。

预设级添加走 `configEditor.edit()`（写 profile 的 `cordis.patch.yml`），工作区级走项目根 `.mcp.json`，两者都不受该启动重写影响，所以用户感知是“有时丢、有时不丢”。

## 修复：插件 SQLite 账本 + 启动后挂回内存

- 新增 `src/mcp-global-store.ts`：使用已有单文件 SQLite 的 `doc` 表，按 profile 存 `mcp/global-servers/<profile>`，形状 `{ version: 1, servers: [{ id, config, disabled }] }`。
- 全局新增：解析/校验通过后先写账本，再调用 root Loader 的 `loader.create()` 在内存中挂载（root tree 的 commit 是 no-op，不写任何配置文件）；HTTP 响应不等 mcp-client 的首次连接（避免 30s startupTimeout 拖住面板）。
- 启动加载：通过 `appReady.onReady()` 在启动成功后把账本中的启用行挂回 root Loader；disabled 行保留在账本但不激活。`appReady` 缺席（裸组装/测试）退回下一个事件循环 tick。
- 全局启停/删除/编辑：宿主配置行优先（按 `entry` 实际操作）；插件账本行的 toggle 先更新 root Loader 再写 SQLite（失败回滚内存），remove 先删 SQLite 再移除 Loader（失败恢复账本），edit 先写账本再更新 Loader（失败回滚账本），避免“本次生效、下次漂移”。
- 状态：插件账本行在 `GET /api/triad/mcp-status` 里带 `config.managed: true` / `config.editable: true`，可继续走既有编辑、启停、删除 UI。
- 升级迁移：账本首次创建时，把确实出现在 profile 根 `cordis.yml` 顶层、且 `configuration()` 的 `inherited` / `override` 都为空、并且存在于 `entry.parent.tree.store` 的旧版 runtime MCP 行收进账本；只执行一次，避免把 home patch / `--patch` overlay 行误收。

## 影响模块

- `src/mcp-global-store.ts`（新）：SQLite 账本读写、校验、CRUD。
- `src/mcp-status.ts`：添加/启动加载/启停/删除/编辑、状态合并、旧行迁移。
- `src/host.ts`：`applyMcpStatus` 变为 async（注册 `appReady` 回调后继续挂其它模块；启动加载等启动成功后再执行，不阻塞宿主启动）。
- 测试：`test/mcp-global-store.test.mjs`（新）；`test/mcp-status.test.mjs` 扩展；`test/workspace-mcp-json.test.mjs` 适配 async apply。

## 验证与反例

- 单测：`npm test` 全量 **190/190 通过**；`npm run build` 成功；`npm run smoke` 宿主/客户端全绿。
- 真实 DSH 回归（临时 web profile，真实 `dsh web --no-open --port 0`）：
  - 添加 `zz-codegraph`（真实 MCP server）→ 工具 `mcp__zz-codegraph__codegraph_explore` 注册成功；
  - 停止进程、重新启动 → 新进程 status 仍显示 `zz-codegraph` 且 `toolCount=1`，`cordis.yml` 始终为模板空数组；
  - `cordis.patch.yml` 未被改写。
- 反例（修复前同流程）：`zz-repro` 添加后出现在 `cordis.yml`，重启后 status 只剩 `anysearch`；说明该检查能红、能抓到这个缺陷。

## 明确不纳入

- 不把全局 MCP 行写回 `cordis.patch.yml`：那会让插件重新承担宿主 YAML 保形、注释保留、`!!js`、锁与 HMR 的整条链路；本插件已有 SQLite 账本，按用户确认的方向使用自有存储。
- 不改预设级与工作区级落盘：前者仍由 `configEditor` 写 profile patch，后者仍是 `.mcp.json`。
- 不做旧数据恢复：已经被 DSH 启动重写抹掉的 `cordis.yml` 行没有备份可恢复；本次只保证升级后不再新增丢失，并迁移热更新时仍存活的行。
